# Master curriculum — raw material, adapt freely

Select, merge, reorder, cut to fit the learner. Each level ends with a boss fight that is a real gate. Every exercise runs on the learner's own long-running project.

## LEVEL 1 — Why long work falls apart *(short — 2–3 sessions — but never skip it)*

- **1.1 Context is a budget, not a memory.** The mental model: the agent doesn't *remember* the project, it *re-reads* whatever fits in its working window each turn. Everything else is gone unless something outside the model puts it back. Why a long session degrades — early detail gets diluted, summarized, or dropped — and why that failure is silent rather than announced. Verify current window behaviour and any memory features in the docs rather than assuming. Exercise: take a long session from their project and identify where the agent started losing the thread, and what it had stopped seeing.
- **1.2 The drift failure.** How a plan quietly becomes a different plan: an assumption made in session two is invisible in session five, so the agent re-derives it differently and both answers look confident. Drift is not the agent being wrong; it is the agent being consistent with less context than you have. Exercise: find one place their project holds two contradictory decisions, and date each one.
- **1.3 Session boundaries as a design choice.** When to keep going and when to start fresh: a fresh session with good notes beats a long session with a full window almost every time. How to recognise the moment — repeated instructions, re-explaining, the agent asking what it already knew. Exercise: end a session deliberately at a good boundary and write the note that makes the next one cheap.
- **1.4 What must survive, and who owns it.** The core distinction: state the *tool* might remember versus state *you* own in a file. Anything the project cannot lose belongs in the second category, because features and limits change. What must survive: the goal, the constraints, decisions and their reasons, what's done, what's next, and what was tried and rejected. Exercise: list everything their project would lose if all chat history vanished tonight, then mark which items exist anywhere else.
- **Boss fight (Level 1):** resume their project cold in a brand-new session, using only what exists outside the chat. Narrate what was missing. Pass = Level 2, and the gaps found here drive the whole level.

## LEVEL 2 — The notes that carry the project

- **2.1 The project file.** One durable brief that answers: what are we building, for whom, what's in and out of scope, what constraints are fixed. Written for a reader with zero context — because in two weeks that reader is them. Where it lives, and why it lives in the repo or project folder rather than in a chat. Exercise: write theirs, then start a fresh session and have the agent work from it alone.
- **2.2 The decision log.** The highest-value artifact in long work and the one nobody keeps: every non-obvious decision, one line, with the *why* and the date. Why "we chose X" is nearly useless without "because Y, and we rejected Z because W" — the reasons are what prevent the decision being silently re-litigated. Exercise: reconstruct the last five decisions on their project from memory and git history, and note how much reasoning is already gone.
- **2.3 Standing instructions.** Project rules every session inherits automatically — conventions, constraints, things never to touch, how to behave when something is ambiguous. In Claude Code that's `CLAUDE.md`; several other agents read `AGENTS.md`; verify the current mechanism for their tool in the docs. Exercise: write theirs, then probe whether behaviour actually changed.
- **2.4 The handoff note.** The last thing written each session: where things stand, what's in flight, what's next, and any trap the next session should know about. Two minutes that save twenty. Exercise: write one at the end of a real session and open the next one with nothing else.
- **2.5 Notes that stay true.** Stale notes are worse than no notes, because they're trusted. How to keep the project file and decision log current without turning documentation into the project — update on decision, not on schedule; delete what's obsolete rather than appending. Exercise: audit their notes for anything no longer true and cut it.
- **Boss fight (Level 2):** hand the project to a fresh session — or a willing human — with nothing but the written artifacts, and have them state the goal, current state, and next step correctly. Pass = Level 3.

## LEVEL 3 — Structuring work that spans days

- **3.1 Slicing into session-sized work.** Cutting a multi-week project into pieces that each fit one session and each end somewhere stable. Why a piece that can't finish in a session will be half-done forever, and how to find a smaller cut. Exercise: slice the next two weeks of their project into session-sized units with a stable end state each.
- **3.2 Checkpoints you can return to.** Commit before, commit after, commit often enough that any session can be undone without argument. For non-code work: dated snapshots, versioned copies, or whatever "a state I can return to" means in their tools. The rule is the same — never let a session be unrecoverable. Exercise: establish a checkpoint rhythm and deliberately roll one back.
- **3.3 Parallel attempts without a mess.** When a project needs two approaches tried, keeping them isolated instead of tangled — branches, git worktrees, separate copies. When parallelism genuinely helps versus when it doubles the state you have to track. (Cross-reference `/ai-docent:mechanics` for the cost side.) Exercise: run one real fork of the project in isolation and kill it cleanly.
- **3.4 When the agent goes sideways mid-project.** Recovery drill: it loops, edits the wrong thing, fills its window with junk, or declares something finished that isn't. Stop it, restore from the last checkpoint, restart the session clean, re-scope smaller, and write down what happened so it doesn't repeat. Exercise: let a session genuinely go wrong, then recover the project calmly.
- **3.5 Keeping the plan honest.** Plans drift because reality moves, which is fine — what kills projects is drift nobody wrote down. The weekly ritual: re-read the project file, note what changed, update or explicitly abandon. Exercise: run one honest plan review on their project and record what actually changed.
- **Boss fight (Level 3):** run a full week of the project under their own scaffolding — slices, checkpoints, notes — and show at the end that any session in that week could be resumed cold. Pass = Level 4.

## LEVEL 4 — Scale, review rhythm, and knowing when to stop *(the graduation level)*

- **4.1 Work that spans repos or workspaces.** The hardest current case: one change that touches several repositories or several bodies of work an agent can't see at once. Techniques: an explicit map of what lives where, one repo at a time with written handoffs, and treating cross-boundary work as its own tracked task. Be honest that tooling here is genuinely weak. Exercise: map their project's boundaries and plan one cross-boundary change deliberately.
- **4.2 The long-project review rhythm.** Reviewing work you didn't just do — you shipped it four days ago and no longer remember why. Reading your own history, using the decision log as the review index, and catching what accumulated rather than what changed. (Cross-reference `/ai-docent:shipping` for reviewing a single change; this is reviewing a fortnight of them.) Exercise: review a week of their own project as if it were someone else's.
- **4.3 What the agent claims versus what happened.** Over weeks, unverified claims compound: things marked done that weren't, tests said to pass that never ran, decisions recorded that were never applied. The periodic audit against reality. (Cross-reference `/ai-docent:reliability` for the verification craft.) Exercise: audit five "done" items in their project against actual state.
- **4.4 Knowing when it's done.** Long projects rarely end; they get abandoned or they sprawl. Defining done in advance, recognising the point of diminishing returns, and choosing deliberately between shipping, parking with good notes, and stopping. Parking well is a skill: a project you can restart in six months is a different asset from one you can't. Exercise: write the done condition for their project, and the parking note they'd leave if they stopped tomorrow.
- **4.5 Graduation — carry a real project across a real gap.** Take their project through a deliberate multi-day break — at least several days, ideally a week — then resume cold, using only the scaffolding they built, and move it forward in that first session without re-deriving anything. Grade honestly: what carried, what was missing, what they reconstructed from their own head rather than their notes. Then write a short "long-haul diploma" — strengths, the artifact most likely to rot, and the three rituals to keep forever. Graduation also produces a one-page **keepable cheat-sheet**: their session-end ritual, their note structure, their recovery drill.

## WOVEN THROUGHOUT (every session, no exceptions)

- The mantra: *the agent re-reads, it doesn't remember; if it isn't written down, it didn't happen; end every session resumable.*
- Every lesson runs on their real project. A course about long work cannot be taught on a toy.
- Own your state. Anything the project can't afford to lose lives in a file you control, not in a feature whose behaviour may change.
- Keep a running **Drift log** — every time something is lost, redone, or contradicted, one line: what happened, what it cost, what would have caught it. Review it at retros; it is the real measure of progress.
- Boring beats clever. The techniques that survive a long project are notes, checkpoints, and rituals — not sophisticated prompting.
- Staying current: memory features, context limits, and session tooling change fast — re-verify against the docs rather than trusting what worked last quarter, and never quote a limit from memory.
